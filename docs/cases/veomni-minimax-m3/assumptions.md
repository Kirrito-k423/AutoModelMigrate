# MiniMax M3 Fact And Assumption Log

**Case:** VeOmni support for MiniMax M3  
**Phase:** 01 VeOmni + MiniMax M3 Intake  
**Status:** Intake evidence, not implementation signoff

This log separates public facts from assumptions that must be verified before any VeOmni adapter, NPU recipe, or optimization work is considered complete.

## Fact And Assumption Table

| Area | Known Fact | Source | Assumption | Risk | Validation Needed |
|------|------------|--------|------------|------|-------------------|
| Model identity | MiniMax M3 is published as `MiniMaxAI/MiniMax-M3` and described as a native multimodal model with 1M context. | https://huggingface.co/MiniMaxAI/MiniMax-M3; https://github.com/MiniMax-AI/MiniMax-M3 | The public repository and Hugging Face artifacts are the intended reference for open-weight integration. | Public files may change while the model is newly released. | Pin exact git commit, Hugging Face revision, model config hash, tokenizer hash, and license before coding. |
| Architecture scale | Public model card states about 428B total parameters and about 23B activated parameters. | https://huggingface.co/MiniMaxAI/MiniMax-M3 | The first VeOmni slice can inspect config and construct a tiny/skeleton path without loading full weights. | Full checkpoint load is too large for early semantic integration and may hide adapter issues behind infra limits. | Inspect config files and determine whether meta-device construction or reduced fixture weights are available. |
| MSA / sparse attention | MiniMax M3 introduces MiniMax Sparse Attention (MSA) for long-context efficiency. | https://huggingface.co/MiniMaxAI/MiniMax-M3; https://arxiv.org/abs/2606.13392 | VeOmni support must model MSA as an attention capability, not as a generic dense-attention fallback. | Dense fallback may run but fail memory/performance gates and give misleading migration status. | Identify official MSA implementation, expected attention mask semantics, KV cache/block layout, and fallback behavior. |
| MSA operator design | The MSA paper describes blockwise sparse attention built on GQA, with an Index Branch selecting Top-k KV blocks and a Main Branch running exact block-sparse attention. | https://arxiv.org/abs/2606.13392 | VeOmni's model adapter needs a capability switch for MSA kernel availability on GPU/NPU backends. | If kernel support is absent on NPU, early training/inference recipes must mark MSA as unsupported or emulated. | Create a BackendAdapter capability row for MSA: unsupported, emulated, native, optimized. |
| Context length | Public sources describe 1M-token context support. | https://huggingface.co/MiniMaxAI/MiniMax-M3; https://github.com/MiniMax-AI/MiniMax-M3 | First validation should use tiny and medium context fixtures before attempting 1M context. | Full 1M tests are expensive and may fail for runtime reasons unrelated to model semantics. | Define staged context gates: tiny smoke, 32K/128K feasibility, 1M performance run. |
| Native multimodality | Public model card states M3 is trained with text, image, and video mixed from the first step. | https://huggingface.co/MiniMaxAI/MiniMax-M3 | VeOmni integration must treat multimodal preprocessing as part of the case, even if first slice is text-only. | Text-only implementation could miss image/video processor contracts and checkpoint components. | Inventory processor files, media token conventions, image/video transforms, and VeOmni multimodal data hooks. |
| Tokenizer | The tokenizer is expected to be provided with the Hugging Face model artifacts, but the exact tokenizer type and special tokens still need inspection. | Assumption from HF-style model packaging; source artifact to inspect: https://huggingface.co/MiniMaxAI/MiniMax-M3/tree/main | VeOmni can load tokenizer through its existing tokenizer builder or a Transformers-compatible path. | Special tokens, chat templates, media tokens, or thinking-mode tokens may diverge from existing builders. | Record tokenizer class, vocab size, special tokens, chat template, BOS/EOS/PAD behavior, and media placeholder tokens. |
| Checkpoint format | Public open-weight distribution is expected to use Hugging Face-style files, but exact sharding, safetensors layout, and index metadata need verification. | Assumption from public HF repository; source artifact to inspect: https://huggingface.co/MiniMaxAI/MiniMax-M3/tree/main | First slice should not require full distributed checkpoint conversion. | Weight naming or MoE sharding may not match VeOmni's loader assumptions. | Build a checkpoint inspection note: file list, shard count, index format, dtype, module-name mapping, MoE expert naming. |
| Precision | Public cards do not by themselves prove the target training/inference precision policy for VeOmni or Ascend NPU. | Assumption; NPU constraints from Ascend/VeOmni docs: https://veomni.readthedocs.io/en/latest/get_started/installation/install_ascend_arm.html | Precision should be selected by backend capability and recipe, not hard-coded in the model adapter. | Precision mismatch can create silent numerical drift or unsupported NPU ops. | Define BF16/FP16/FP32/FP8 or vendor-specific precision support per backend before accuracy signoff. |
| Inference scope | Public model card includes local deployment/inference sections, but this project is targeting VeOmni as the first framework path. | https://huggingface.co/MiniMaxAI/MiniMax-M3 | The first useful VeOmni slice should be model construction plus tiny forward/inference smoke, not full serving. | Serving-first work may drag in vLLM/SGLang-specific concerns before VeOmni contracts are clear. | Decide whether first smoke uses official HF forward, VeOmni task script, or a minimal adapter harness. |
| Training scope | VeOmni is positioned for pre-training and post-training across single/multimodal models. | https://github.com/ByteDance-Seed/VeOmni; https://veomni.readthedocs.io/en/latest/ | Full M3 training is out of scope for Phase 1; training support begins with recipe/interface mapping. | Claiming training support before data, checkpoint, distributed, precision, and loss gates exist would be unsafe. | Map required VeOmni training hooks: model init, data transform, loss, optimizer, FSDP/EP/SP, checkpoint save/load. |
| VeOmni model integration | VeOmni docs expose model/task/config extension points such as training scripts, argument parsing, data builders, model/tokenizer builders, and parallel state. | https://veomni.readthedocs.io/en/latest/usage/basic_modules.html | MiniMax M3 can be approached through the same extension surface after model-specific config and processor gaps are mapped. | MSA and multimodal contract may require new model registry or ops configuration fields. | Identify exact files/symbols in VeOmni source for model registration, tokenizer build, data transform, and ops implementation. |
| Ascend A2 / 910B runtime | VeOmni upstream includes an Ascend A2 Docker guide using CANN 9.0.0 910B images and x86/ARM Dockerfiles. | https://github.com/ByteDance-Seed/VeOmni/blob/main/docs/hardware_support/AscendDockerUsage/build_a2_docker.md | On this ARM64 host, the VeOmni A2 ARM Dockerfile should be the preferred container baseline after device/root access is verified. | Building/downloading images may consume significant traffic and disk; host `npu-smi` currently needs root. | Verify root-level `npu-smi info`, Docker device access, base image pull feasibility, and disk/network budget before build. |
| Evaluation | No task-level MiniMax M3 acceptance set has been selected yet. | Assumption from project scope | Accuracy validation should compare against official outputs or a pinned reference implementation once available. | Without a declared baseline, "works" can hide tokenizer, checkpoint, MSA, or multimodal drift. | Choose golden prompts/media fixtures, expected outputs/logits where possible, and drift thresholds. |

## Open Assumptions To Close First

1. Exact Hugging Face revision, config schema, tokenizer files, and checkpoint index.
2. Whether MiniMax's official MSA kernel/API is available and portable to Ascend NPU.
3. Whether VeOmni already has enough Transformers v5/model registry hooks for M3 or needs new adapter boundaries.
4. Which first slice is safer: text-only construction/forward smoke or multimodal processor inventory plus text smoke.
5. Which root-approved path should be used to capture `npu-smi info` on this machine.
